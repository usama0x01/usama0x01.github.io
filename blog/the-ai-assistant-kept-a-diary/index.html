The AI assistant kept a diary.

Local LLM tooling has quietly created a new forensic artifact: a plaintext, timestamped, uncensored record of exactly what someone was trying to build. Investigators should know it exists. So should everyone else.

DFIRLLM SecurityInsider RiskForensics·4 November 2026

01A new artifact class

Digital forensics is the business of reconstructing intent from residue. Browser history, shell history, prefetch, jump lists, LNK files: none of them record what someone meant to do. They record what they touched, and an investigator infers the rest.

Local LLM tooling broke that pattern. When somebody designs a tool by conversing with a model running on their own machine, the conversation is the design document. It is written in plain language, it is timestamped, it names the goal explicitly, and in most default configurations it is never cleared.

The uncomfortable bit

Shell history tells you a command ran. A prompt history tells you why, who it was aimed at, what the author was worried about, and frequently the passphrase they chose.

02What this looks like in practice

The cleanest illustration I have run into came from a forensics challenge in the BlackHat MEA 2026 qualifiers, Whisper. The scenario: a Linux workstation, an insider who used a local LLM to build an exfiltration tool. No memory corruption, no clever cryptography. The entire challenge is artifact retention.

Three failures compose, and all three are default behaviour rather than mistakes:

  1. The prompt log is plaintext and permanent. ~/.ollama/history is never cleared. It contained a step-by-step statement of intent and the passphrase, typed straight into the chat.
  2. "Delete the script after execution" was implemented as a move to Trash. The tool survived intact in ~/.local/share/Trash/files/, alongside a .trashinfo file recording the deletion timestamp.
  3. The staging directory was a cache folder nobody cleans. The archive was still there.

The forensic path is almost comically short: grep the prompt history for intent, recover the script from Trash to learn the key derivation, find the archive where the script says it staged it, derive the password, open it. The interesting part is not the technique. It is that the most incriminating artifact on the disk was created by a productivity tool, silently, as a feature.

Two properties make these unusually valuable. They are narrative, so they describe intent directly instead of requiring inference. And they are pre-redaction, because people paste real secrets, real hostnames and real customer data into a model they believe is private and local.

04What it means for everyone else

Flip it around, because this cuts both ways.

For defenders: a local model is not a private one in any sense that matters forensically. It does not phone home, which is the fear people actually have, but it writes an unusually candid record to disk, which is the risk nobody budgeted for. If your data-classification policy covers documents and chat messages but not prompt histories, it has a hole in it the size of your engineering team.

For insider-risk programmes: this is the highest-signal artifact you are currently not collecting. It is also exactly the kind of monitoring that needs a written policy and legal review before you touch it, because the same file that proves exfiltration also contains somebody's half-finished questions about a medical condition. Collect it deliberately or not at all.

For everyone using these tools: assume the transcript is permanent and discoverable. Do not paste production credentials into a local model to save thirty seconds. The model will not leak them. The log file might.

Investigators spent two decades learning to reconstruct intent from fragments. The tooling now just writes it down. That is a gift and a liability, and which one it is depends entirely on which side of the disk image you are standing on.
