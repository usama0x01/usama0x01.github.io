Challenge 4 of 15 Forensics Full writeup

BlackHat MEA 2026 · Qualifiers

Qfact.

Windows host triage: encrypted user files, Defender quarantine, event logs, registry hives.

Forensics· 4 November 2026

TL;DR

Windows Defender quarantined the ransomware but the evidence set ships the quarantine store. Decrypt the quarantine with the static MsMpEng RC4 key, read the AES key out of the dropper, rebuild the IV from host identifiers found in the registry, and decrypt the victim files.

Captured

01Recon

The evidence archive is a classic Windows triage collection:

The ransom note names the victim: Your Unique ID: LOCK-DESKTOP-KLPAT9O-JM-20260628-7F3A.

The.enc files carry no magic bytes, no salt and no IV, every length is an exact multiple of 16. That rules out a self-describing container and means the key material has to come from somewhere else in the image. The Quarantine/ tree is that somewhere: Defender caught the dropper and kept a copy.

02The bug

Two design decisions in the ransomware make full recovery possible:

  1. The AES key is a hard-coded literal in the dropper, obfuscated only by Chr() concatenation, and the dropper itself survives in Defender's quarantine store.
  2. The IV is derived from non-secret host identifiers, MD5(COMPUTERNAME + USERNAME), both of which are recoverable from the registry hives in the same evidence set (and the computer name is printed in the ransom note).

Defender's quarantine store is itself only obfuscated, not encrypted: every file is RC4 with a static, publicly documented 256-byte key compiled into MsMpEng.

03Exploitation

  1. Decrypt the quarantine store. RC4 each of the three files with the static MsMpEng key. The ResourceData entry parses as:

The payload is a 4,557-byte HTA, Q3 Financial Review - Loading, carrying a VBScript Window_OnLoad that builds and runs a PowerShell one-liner.

  1. Read the crypto out of the dropper.

which is Fx7mK9vL2nQ4wPz!. The PowerShell then does:

So: AES-256, key = "Fx7mK9vL2nQ4wPz!" right-padded to 32 bytes with spaces. $a.Mode = 0 is not a valid CipherMode; the assignment throws and is swallowed by $ErrorActionPreference='SilentlyContinue', so the mode stays at.NET's default, CBC. Padding = 2 is PKCS#7.

  1. Rebuild the IV. COMPUTERNAME is DESKTOP-KLPAT9O (ransom note, confirmed in Registry/SYSTEM). For USERNAME, the note only gives the first two letters uppercased (JM); the profile path in the hives gives it exactly:

IV = MD5("DESKTOP-KLPAT9O" + "jmartin") = a31de3916e88f240c2bf08735b965aa9.

  1. Decrypt and read. All 9 files decrypt to clean UTF-8 with valid PKCS#7. The flag is in Q3_auth_memo.txt, base64-encoded "for secure internal transmission":

Key code KEY = bytes([0x1E,0x87,0x78,0x1B,0x8D,0xBA,0xA8,0x44...]) # 256-byte static MsMpEng RC4 key

04Dead ends

  • PKCS#7 validity does not confirm the IV. In CBC the final block depends only on the previous ciphertext block, so every IV candidate passes a padding check. Three candidate usernames all gave 9/9 valid padding; only inspecting the first plaintext block distinguishes them.
  • $a.Mode = 0 looks like ECB at a glance (in some libraries 0 means ECB). In.NET, CipherMode has no member 0; the property setter throws and SilentlyContinue hides it, so the effective mode is the default CBC. Decrypting as ECB produces garbage in every block.
  • The Quarantine/Resources and Quarantine/Entries files unpack with a per-section RC4 stream rather than one continuous stream; only ResourceData is needed, so this never had to be resolved.
