Challenge 13 of 15 Web Solved · 100 pts

BlackHat MEA 2026 · Qualifiers

Lumen.

Lumen is a read-only document relay with a content security policy locked down on every page, so the operator is confident that even a stray reflection cannot run. Sign in is not your problem. The operator is, and the operator keeps something valuable in their browser. Find the reflection, get it to run despite the policy, and convince the operator to hand it over.

Web· 100 points· 4 November 2026

TL;DR

A < is smuggled into the ?p=view 404 reflection across the dir/file parameter boundary, because index.php calls urldecode() on the concatenation after each half was sanitised separately; the strict per-request nonce CSP is then deleted entirely by sending >1000 query parameters, which makes PHP print a max_input_vars request-startup warning before the script runs, so header("Content-Security-Policy: ...") fails with "headers already sent". The resulting unrestricted onerror handler reads the operator bot's localStorage.flag and posts it to the app's own ?p=trace note store, which the attacker reads back.

02The bug

Three distinct bugs, all required.

  1. Decode-after-sanitise, split across two parameters (?p=view)

Two compounding errors:

  • urldecode() runs after htmlspecialchars(), so %3e, %22, %27, %26 in the input are resurrected into >, ", ', & in the output, the escaping is undone.
  • dir and file are cleaned separately but concatenated before decoding. dir ending in % and file starting in 3c means neither half ever contains the blocked string %3c, yet the joined string does. dir=docs/%25 decodes (by PHP's own $_GET handling) to docs/%; file=3c... stays 3c...; the concatenation is docs/%3c... and urldecode() turns it into docs/<....

Everything after the smuggled < is supplied double-URL-encoded so it survives two decode passes: $_GET strips one layer (leaving only % -hex and alphanumerics, which pass both the %3c blocklist and htmlspecialchars untouched), and urldecode() strips the second, yielding raw ", =, spaces and > in the echoed $path.

  1. CSP deletion via max_input_vars startup warning

max_input_vars=1000 is enforced during PHP request startup, before a line of index.php executes. With display_errors=1 and output_buffering=0, that warning is written straight to the response body, which flushes the HTTP headers. header() on line 3 then cannot run:

HTTP/1.1 200 OK X-Powered-By: PHP/8.3.33 Content-type: text/html; charset=UTF-8

<b>Warning</b>: PHP Request Startup: Input variables exceeded 1000. To increase the limit change max_input_vars in php.ini. in <b>Unknown</b> on line <b>0</b><br /> <b>Warning</b>: Cannot modify header information - headers already sent in <b>/app/public/index.php</b> on line <b>3</b><br />

No Content-Security-Policy header at all. The nonce architecture is bypassed not by guessing or stealing the nonce but by preventing the policy from ever being sent, inline onerror= then executes normally.

  1. ?p=trace as an unauthenticated shared note store

Any client can write (&note=) and any client can read (no note) the same id. The bot writes the flag under id=lumenpwn01; the attacker reads it back from the same endpoint. Same-origin, so it also satisfies img-src 'self' had the CSP survived.

03Exploitation

  1. Build the injected HTML. Everything after the single smuggled <:

Double-URL-encode it (quote(quote(s, safe=''), safe='')) so it passes clean() as inert % -hex text and only materialises after urldecode().

  1. Smuggle the < across the parameter boundary.

$_GET['dir'] = docs/%, $_GET['file'] = 3cimg%20src%3Dx%20onerror%3D%22...%22%3E. Neither matches / %3c/i; htmlspecialchars is a no-op on both. urldecode("docs/%". "3cimg%20...") yields the live tag. Verified against the local container:

  1. Kill the CSP. Append 1100 dummy parameters (a0=1&a1=1&…&a1099=1), pushing the request over max_input_vars=1000. Response comes back with the two PHP warnings and no Content-Security- Policy header. Final URL is ~8004 bytes, well inside the PHP built-in server's request-line limit.

It matches ^https?:// and has no control characters, so it is queued. bot.js picks it up within ~1s, seeds localStorage.flag on http://127.0.0.1:5000/?p=home, rewrites the URL's host via localise() to that same origin, and loads it. The <img src=x> fails, onerror fires with no CSP to stop it, and reads localStorage.getItem('flag') from the bot's own origin.

04Dead ends

  • The chain was derived statically from the handout and validated in one pass against a local docker compose build, so there were no failed exploitation attempts. The two things that could have burned time were both settled by reading application/run and bot.js rather than by probing:
  • Nonce-stealing is a dead end by design. The nonce is bin2hex(random_bytes(16)) regenerated per request and never reflected anywhere reachable, so any approach based on leaking or reusing it fails. The intended primitive is suppressing the header, and the only hint is the deliberately odd -d display_errors=1 -d output_buffering=0 -d max_input_vars=1000 flag set in application/run, easy to skim past when reading only index.php.
  • External-host exfiltration is a dead end too. bot.js's localise() rewrites any submitted URL's origin to http://127.0.0.1:5000, and img-src 'self' would have blocked an outbound beacon anyway;?p=trace is the intended in-band channel.
  • Single-URL-encoding the payload does not work: $_GET already performs one decode, so the tag would arrive at clean() as literal < / " / > and be neutralised by htmlspecialchars. The payload must be double-encoded so it is still inert % -hex when clean() inspects it, and only becomes markup at the later urldecode().
  • The local container has no /flag.txt, so it yields only BHFlagY{local_test_flag} from DYN_FLAG, the real flag required running the finished script against the live instance.
  • Instances are per-session: the two flags listed correspond to two different playat.flagyard.com hosts, with the identical unmodified exploit run against each.
