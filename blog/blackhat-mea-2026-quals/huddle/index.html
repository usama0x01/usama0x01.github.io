BlackHat MEA 2026 · Qualifiers

Huddle.

Huddle is a small team chat workspace. Members post in channels, invite teammates with a shareable link, and the workspace owner can switch on extra features such as video messages. You arrive as an ordinary member. Work your way into the owner's seat, then turn the workspace's own tooling into a window onto the server.

Web· 4 November 2026

TL;DR

Huddle signs invite tokens with sha256(secret ‖ "team=main&email=…&role=member") and parses them with a hand-rolled last-duplicate-key-wins splitter, so a SHA-256 length-extension appending &role=owner promotes any member to workspace owner. Owner unlocks the video- message thumbnailer, which shells out to ffmpeg -enable_drefs 1 -use_absolute_path 1; a hand- built MP4 with a Mac-alias (alis) external data reference plus a custom 256-entry pal8 colour table turns each thumbnail into one JPEG-lossless bit-plane of an arbitrary server file, and 8 requests reconstruct /flag.txt byte-exact.

02The bug

Bug 1, invite token signed with a raw SHA-256 prefix MAC over an attacker-extendable message. GET /api/invite returns token = b64url("team=main&email=" + user.email + "&role=member") and sig = sha256(SECRET ‖ token_plaintext), a length-extension-vulnerable construction, not HMAC. POST /api/join verifies sig over the decoded plaintext and then applies the token's role to the token's email (an unknown email gives {"error":"no such member email"}), so a member can rewrite their own role if they can forge a signature.

The parser makes it exploitable in exactly one direction: it is a hand-rolled split('&') / split('=') where the last duplicate key wins. The server-controlled role=member is the last field of the legitimate message, so injecting &role=owner through the email field lands before it and is overwritten:

Length extension appends after everything, including the glue padding, so the injected role=owner becomes the final occurrence and wins:

The secret length is the only unknown, and it is directly brute-forceable because the "invalid invite signature" error is a clean oracle (20 bytes on instance 1, 17 on instance 2, randomised per deployment).

Bug 2, owner-gated thumbnailer runs FFmpeg with -enable_drefs 1 -use_absolute_path 1. Those two demuxer options re-enable QuickTime external data references: the moov/trak/mdia/minf/dinf/dref box may point sample data at a file outside the container. In libavformat/mov.c (n5.1.3), mov_read_dref() only honours MKTAG('a','l','i','s') records with size > 150; a url entry falls into the else branch that decrements entries / i and drops it silently, so the "obvious" url -dref exploit does nothing. Inside an alis record, a variable-length record of type == 2 sets dref->path (absolute path), and mov_open_dref() takes the absolute-path branch when nlvl_to == 0 || nlvl_from == 0:

with test_same_origin() /.. /: filtering bypassed entirely (those only guard the relative branch when use_absolute_path is 0). With the sample description set to codec raw and stsz / stco under attacker control, the decoded frame is the raw bytes of any server file, at any offset.

Bug 3 (exfil channel), lossy JPEG output defeated with a custom palette. The thumbnail is JPEG, so mapping one file byte to one gray8 pixel destroys the data (measured: max error 10, mean 1.89, only 25.6% of bytes exact). The QuickTime raw sample description with depth = 8 decodes as pal8 and, when the colour-table id field is 0 instead of -1, an inline 256-entry colour table follows in the sample description. Setting entry i to pure black or pure white according to bit k of i makes every pixel a JPEG-survivable extreme, so one request yields one exact bit-plane and 8 requests yield the file byte-for- byte.

03Exploitation

  1. Register and pull a signed invite
  1. Confirm the parser is last-wins (via the parsed oracle)

POST /api/join with any bogus sig echoes parsed. …&role=owner&role=member → member; … &role=member&role=owner → owner. Appending after the message is therefore the winning position. (Registering with email = "pwn3@x.com&role=owner" and joining yields {"ok":true,"email":"pwn3@x.com","role":"member"}, injection alone is useless.)

  1. SHA-256 length extension → owner

No hash_extender / hashpumpy on the box, so SHA-256 was reimplemented in pure Python (sha256ext.py: compress(), padding(msglen) = b"\x80" + b"\x00"*((55-msglen)%64) + pack(">Q", msglen*8), extend(orig_hex, orig_len, append) seeding the state from the 8 words of orig_hex). Self-test against hashlib passed.

Brute-force the secret length 0–79, forging sig' = sha256_extend(sig, klen+len(qs), b"&role=owner") and token' = b64url(qs ‖ padding(klen+len(qs)) ‖ "&role=owner"), and POST each to /api/join with your own session cookie:

(Extending the base64 string instead of the decoded query string, the b64 mode in the first script, never validates; the MAC is over the raw plaintext.)

  1. Unlock the thumbnailer
  1. Build an MP4 with an alis external data reference (mkdref.py)

Minimal QuickTime file: ftyp('qt ') + moov(mvhd + trak(tkhd + mdia(mdhd + hdlr'vide' + minf(vmhd + dinf(dref) + stbl)))). The dref holds one alis entry laid out to match mov_read_dref()'s fixed skips:

nlvl_from = nlvl_to = 0 forces the use_absolute_path branch. stsd carries a raw sample entry with data_reference_index = 1, stsz.sample_size = fsize, stts one entry, and stco chunk offset = the read offset inside the external file, i.e. arbitrary offset control. Local verification:

Depth field → pix_fmt map (measured with ffprobe): 1/2/4/8/33/34/36/40 → pal8, 16 → rgb555be, 24 → rgb24, 32 → argb. Depth 8 = one file byte per pixel.

  1. Beat JPEG with a bit-plane palette

Patch the builder to emit an inline colour table: set the sample entry's colour-table-id to 0 (instead of -1) and append pack('>IHH', 0, 255, 255) followed by 256 entries of pack('>HHHH', 0xffff, r*257, g*257, b*257); also change the frame-size formula to (width*(depth & 0x1f)+7)//8 * height. Palette for bit k: entry i = white if (i >> k) & 1 else black. Local check on a 4096-byte file: jpeg match 1.0 (perfect), versus 0.256 exact for the naive gray8 mapping.

  1. Read files

Per request: build the MP4 for path/offset/bit, POST /api/files/upload (raw body), POST /api/files/ thumbnail, GET /thumbnails/<hash>.jpg, threshold luma at 128 → one bit-plane. OR the 8 planes together.

Multi-row frames desync on the server's FFmpeg 5.1 pal8 line stride (64x16 read of /etc/passwd dropped bytes at every row boundary: daemon:x:1:1:daemon:/usr/sbin:/u/nologin), so all reads use height 1, width N, clean up to 8192 bytes per request, zero-padded past EOF. Reads are deterministic and reproduce identically across runs.

A nonexistent path returns {"error":"could not generate a thumbnail for this clip"}, giving a free file- existence oracle:

  1. Flag

Verified at three read widths (128 / 2048 / 8192). Second instance, driven end-to-end by a single pwn.py <url> (register → length-extend → enable video → read) in ~15 s, secret length 17, and re-verified with a fresh account at a different width:

04Dead ends

  • Parameter injection alone fails. Registering email = "pwn3@x.com&role=owner" produces team=main&email=pwn3@x.com&role=owner&role=member; the oracle showed last-wins, so the server's trailing role=member overrides it. role[]=owner, ROLE=owner, and role=owner%00x (no URL-decoding) were all dead ends.
  • Signature type confusion is a dead end. sig: null and sig: 0 → {"error":"token and sig required"}; sig: true / [] / {} → normal invalid invite signature. No undefined / NaN bypass.
  • Length-extending the base64 string instead of the plaintext. The first attack.py ran both a raw and a b64 mode; only raw (extend the decoded query string, then re-encode) ever verified.
  • First length-extension run returned not authenticated, the ad-hoc Netscape-cookie-jar parser built a malformed Cookie header. Fixed by hardcoding sid=7898300f8c9364e1a170ce7eec47bd5702dd8cbe9e508b94 from cA.txt; the final pwn.py uses http.cookiejar + HTTPCookieProcessor instead.
  • No hash-extension tooling installed (hash_extender, hashpump, hashpumpy all missing) → SHA-256 compression function and MD-padding written by hand and self-tested against hashlib.
  • All the classic FFmpeg LFI payloads are blocked by the ftyp magic gate. neex's gen_xbin_avi.py AVI+M3U+XBIN, plain HLS.m3u8 pointing at file:///etc/passwd, and ffconcat version 1.0 / file /etc/passwd were all uploaded and all returned could not generate a thumbnail for this clip in ~0.44 s (no timing difference vs /dev/zero, so not even a blind read). PNG/JPG/GIF/AVI/ WebM/SVG rejected too; only ftyp -prefixed MP4/MOV pass.
  • file_id is not injectable.../../etc/passwd, /etc/passwd, F00000002; id → {"error":"no such file"}.
  • Static-file enumeration is useless, the SPA catch-all returns index.html (200, 18191 bytes) for / server.js, /package.json, /.git/HEAD, /flag.txt, /uploads/…, so 200 means nothing.
  • url drefs do nothing. Reading mov.c n5.1.3 showed the non- alis branch just logs Unknown dref type and decrements the entry count; only a Mac-alias record with size > 150 reaches mov_open_dref().
  • Naive byte-as-pixel exfil is lossy. gray8 through the server's JPEG encoder: max error 10, mean 1.89, 25.6% of bytes exact (root:x:0:0:root:… came back as ppot8z71:58onqv;0…). monow 1-bit rawvideo survives JPEG but is unreachable, depths 1/2/4/8 all decode as pal8, which is what led to the palette trick instead.
  • Multi-row frames desync on the server. 64x64 / 64x16 reads dropped bytes at each row boundary under the server's FFmpeg 5.1 pal8 line stride (locally on FFmpeg 8.1 the same file read cleanly, masking the bug). Switching to height 1 / width N fixed it; 8192 bytes per read verified.
  • Short files corrupt full-frame reads locally, a 3256-byte /etc/passwd in a 4096-pixel frame matched only ~50%; testing with a 16 KB big.bin gave 100%, isolating the issue as short-read rather than palette failure.
  • The secret length is per-deployment (20 on the first instance, 17 on the second), so it must be brute-forced each time; pwn.py sweeps 0–79 automatically.
  • The second host was recycled shortly after the solve (nginx 404 on every path) when asked to re-attack it fresh, the flag had already been captured and verified twice.

Appendix A, Cross-cutting notes Dynamic flags

Most FlagYard instances set FLAG_VALUE="$DYN_FLAG", minting a fresh flag per deployment. Every exploit in this report is therefore written to recover the flag rather than to assert a constant, and several sections list two different flags captured from two different instances of the same challenge.

Instance lifetime

Live instances expire without closing the socket. A dead PWN instance still accepts the TCP connect and then sends nothing; a dead web instance returns connection refused after a handful of probes. When an exploit that previously worked suddenly produces silence, the first hypothesis should be an expired instance, not a broken exploit.
