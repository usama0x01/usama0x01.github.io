Challenge 10 of 15 Reversing Solved · 100 pts

BlackHat MEA 2026 · Qualifiers

free-agentic-tool.

A “free” AI agent CLI, its session debug bundle, and a packet capture of the traffic it produced.

Reversing· 100 points· 4 November 2026

TL;DR

The distributed binary is a dropper. Its real payload is a reflectively-loaded second Go executable that speaks gRPC to a C2, and that stage derives its X25519 private key from <code>sha256(USERNAME + "_" + COMPUTERNAME)</code> instead of generating one, so the whole captured session decrypts from the pcap alone.

Instances are provisioned per run, so these are the values our instances returned.

01Recon

Three artifacts ship together:

free-agent.exe is Go with an intact pclntab, so app symbols (fagent/internal/...) survive. The load- bearing tooling detail: Ghidra headless must be given -processor x86:LE:64:default -cspec golang. With the golang compiler spec the decompilation is near-source quality and Ghidra recovers each function's real file:line from pclntab; with the default windows cspec every Go register-ABI argument decompiles as unaff_RBX / extraout_RAX noise. Applying the 4,801 recovered symbols created 1,557 functions and renamed 3,244.

Scanning every e8 rel32 in.text for crypto/aes.NewCipher gives exactly one application call site, in diagnostics.writeFieldFiles @ 0x4ede60:

The key is a plain static array, not derived, VA 0x871580, file offset 0x46f180:

6e1ac4f78b33905ed20f77a94cb821e63d9512da607ecf1b48a3590ce42db673

Only two instructions in the whole binary reference 0x871580, and nothing writes it. diagnostics.sealValue @ 0x4edbc0 confirms the container format: iv(16 from crypto/rand) then AES-256-CBC(key, iv, PKCS#7(value)).

All 15 zip entries decrypt with valid padding, and none contains the flag. user_input.txt is just /help. The real yield is the victim identity: user lightlight on DESKTOP-DD6SS6U. The stage-1 binary contains no gRPC code at all, so it cannot be what produced the capture.

02The bug

Two bugs, one hiding the other.

  1. free-agent.exe is a dropper, and its loader is disguised as archive/zip. The binary's archive/zip package contains seven functions that do not exist in the Go standard library, all claiming source archive/ zip/writer.go:666+:

Together they are a reflective PE loader, triggered by a planted sync.Once in (*Writer).compressor. The UI meanwhile prints a fake HTTP 401 as cover.

initDeflate decompiles to readStream(payload, &DAT_00871580, 0x20), the diagnostics AES key is reused as the loader's XOR key. The payload is a []byte at global 0xf6f610 pointing at 0x8a1d40 (file offset 0x49f940), 0x6cc5ad bytes, magic FALZ\x01:

That yields a 9,649,152-byte PE32+ (Go 1.20.5, 10,876 functions) which does contain real gRPC and protobuf. flushStream maps it with VirtualAlloc(base, SizeOfImage, MEM_COMMIT|MEM_RESERVE, PAGE_EXECUTE_READWRITE), applies relocations and imports, then jumps to its entry point. Every DLL and procedure name is built byte-by-byte via makeslice + slicebytetostring in archive/zip.init, so none of them appear as strings.

  1. Stage 2 never generates a key pair. In stage 2, main.OOGOOOGOGOOOGGOOO @ 0x8617a0 does:

and feeds that straight into crypto/ecdh.(*x25519Curve).NewPrivateKey. GenerateKey is never called. The private key is a deterministic function of two values that are printed in the capture's own handshake, which is the "unlimited tokens" joke and the actual vulnerability.

03Exploitation

  1. Unpack stage 2. Carve the FALZ blob, LZSS-inflate, unmask with the stage-1 AES key, and write out falz_decoded.bin, the gRPC-speaking stage-2 PE.
  2. Locate the crypto in stage 2. Its protobuf lives in package gogogooogogogo/gogoogogoo with type and method names made only of the letters G and O; main.* (0x849e20–0x86df0f) is obfuscated with control-flow flattening and MBA arithmetic (the dispatcher uses the murmur3 finalizer constants 0xff51afd7ed558ccd and 0x94d049bb133111eb). Ghidra headless with the golang cspec still decompiles it.
  3. Recover the private key from the pcap. The Init message carries agent@DESKTOP-DD6SS6U, and the diagnostics bundle gave the username:

which is an exact match for Init field 2 in the capture. The derivation is confirmed.

Key code def unfalz(buf, key): assert buf[0:4] == b"FALZ" and buf[4] == 1 n = int.from_bytes(buf[6:10], "big") inner = lzss_inflate(buf[10:10+n]) # outLen = BE32(src[0:4]) return bytes(((inner[i] ^ key[(7*i + 3) % 32]) - key[i % 32]) & 0xFF for i in range(len(inner)))

04Dead ends

  • Ghidra without -cspec golang is unusable here. Every Go register-ABI argument decompiles as unaff_RBX / extraout_RAX. The spec id is golang in Ghidra/Processors/x86/data/languages/x86-64- golang.cspec.
  • The stage-1 AES key is not derived. Time was spent looking for a Getenv / sha256 / hkdf derivation near the NewCipher call. There is none, it is a static array, and the same 32 bytes are reused as the dropper's XOR key.
  • Decrypting the debug bundle is a dead end for the flag. All 15 entries decrypt cleanly and none contains it; their value is the victim identity that the key derivation needs.
  • The hostname in the task brief had a typo (DESKTOP-DD6SS6EU). The capture's Init says agent@DESKTOP-DD6SS6U (21 bytes, 0x15), and only the correct spelling makes the key derivation reproduce the observed public key.
  • report.tryUpload POSTs to http://not-malicious-website.ctf/upload, a decoy that never appears in the capture.
  • AAD matters: GCM verifies with empty AAD; passing the sessionID as AAD fails every frame.
