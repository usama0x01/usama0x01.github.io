Fifty-nine CVEs in one year: what WordPress plugins keep getting wrong.

I spent a year reporting WordPress plugin vulnerabilities through WPScan. Fifty-nine CVE IDs later, the same mistake keeps showing up in three different costumes.

WordPressAppSecVulnerability ResearchREST API·4 November 2026

01The corpus

Between late 2024 and November 2026 I reported WordPress plugin vulnerabilities through WPScan under coordinated disclosure. That run produced 59 assigned CVE IDs, of which 51 are catalogued publicly on my research page and 55 advisories are live. It also put me 9th on the WPScan researcher leaderboard.

That is a large enough sample to stop telling anecdotes and start counting. So I counted. Here is what 51 vulnerabilities across 46 distinct plugins actually look like when you line them up.

The short version

Half of these bugs are the same bug. A plugin exposes an endpoint, carefully verifies that the request is well-formed and that the user is logged in, and never checks whether that particular user is allowed to do that particular thing to that particular object.

53% need no account at all. Another 22% need only a Subscriber account, which on any site with open registration is the same thing as unauthenticated with one extra HTTP request. Put those together and roughly three quarters of these bugs are reachable by someone who walked in off the street.

The severity distribution is the part people get wrong about this category of research. Most of these are not remote code execution. They are a booking system that returns other customers' bookings, a gift-card plugin that returns live card codes and buyer PII, a directory plugin that returns the users table. Individually unglamorous; collectively, a breach notification.

03One mistake, three costumes

Nearly every access-control finding in the corpus reduces to the same confusion: authentication is not authorisation, and a nonce is neither. It just wears a different outfit depending on which WordPress API the developer reached for.

Costume one: the REST route with no permission callback

Eight of the catalogued CVEs live on REST routes. register_rest_route() takes a permission_callback, and since WordPress 5.5 omitting it throws a notice. The notice is easy to silence in the worst possible way:

That is literally how an unauthenticated database export ships. __return_true is not a permission check; it is the absence of one, spelled in a way that passes code review because it looks like a decision.

Costume two: the nopriv AJAX handler

Ten of the findings sit on admin-ajax.php handlers. WordPress makes you register two hooks, and the second one is a loaded gun:

The _nopriv_ variant exists for genuinely public actions, and it gets copy-pasted onto handlers that read private data because the developer was debugging a logged-out edge case and never took it back out. The handler itself is usually fine for its intended caller. It simply never imagined an unintended one.

Costume three: the nonce that was mistaken for a permission

This is the subtlest and the most common. The code looks defensive:

A nonce proves the request came from a page your site rendered for this user. It says nothing about whether this user may touch item $id. Any logged-in Subscriber can load a page that mints a valid nonce, then point the request at somebody else's object. That is the entire mechanism behind the IDOR findings in this corpus, and it is why check_ajax_referer appearing in a function is not evidence that the function is safe. It is evidence that the developer thought about CSRF, which is a different attack.

04Finding them

None of this requires exotic tooling. The workflow that produced the corpus is boring on purpose, which is why it scales:

  1. Enumerate the surface. Grep the plugin for register_rest_route, wp_ajax_nopriv_, add_action( 'admin_post_nopriv_, and add_shortcode. That list is the attack surface, and it is usually under thirty entries.
  2. For each entry, ask one question. Not "is this sanitised" but "which user is allowed to call this, and where is that enforced?" If the answer is a nonce check, you have probably found a bug.
  3. Reproduce locally. A local WordPress with the plugin installed, two accounts (Subscriber and Administrator), and a logged-out browser. Call the endpoint as all three.
  4. Deduplicate before reporting. Check NVD, the WPScan database and Patchstack for the plugin and version. Reporting a known bug burns your credibility and the triager's afternoon.
  5. Report privately, publish nothing. WPScan handles vendor coordination and CVE assignment. Nothing goes public until a fix ships.

Search-engine reconnaissance narrows step one considerably. I keep the queries I actually use in a public dork library; the WordPress section at the top is the one that fed this research.

05If you ship a plugin

Four things, in descending order of how much grief they will save you:

  • Every permission_callback gets a real capability check against a real object. If you wrote __return_true, you shipped a public endpoint; make sure you meant to.
  • Audit every _nopriv_ hook you have. For each one, write down in a comment why an anonymous caller is acceptable. If you cannot finish the sentence, delete the hook.
  • Treat nonces and capabilities as unrelated. They defend against different attacks. You need both, and having one tells you nothing about the other.
  • Check the object, not just the verb. current_user_can('edit_posts') is a role test. current_user_can('edit_post', $id) is an authorisation decision. The second argument is where IDOR goes to die.

Fifty-one vulnerabilities, 46 plugins, one missing line. The WordPress plugin ecosystem is not insecure because it is hard to secure. It is insecure because the API makes the unsafe thing shorter to type.
