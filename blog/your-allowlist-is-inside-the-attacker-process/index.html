Your allowlist is inside the attacker's process.

A CTF challenge taught me the cleanest statement of a bug class I keep finding in production: network-level allowlists that sit in front of a service the attacker is already executing inside.

AppSecCloudCI/CDSSRF·4 November 2026

01The shape of the bug

There is a control pattern that looks like security and is not: restricting access to a privileged service by where the request appears to come from. Bind it to loopback. Allowlist an IP. Check that the source is inside the VPC. Ship it.

It fails whenever the attacker gets to run code in the trusted location. And in modern architectures, the attacker gets to run code in the trusted location far more often than the design assumed.

02The clean example

I hit the purest version of this in the BlackHat MEA 2026 qualifiers, in a challenge called DeckForge. The service turns attacker-supplied HTML into preview images. Three decisions compose into a full compromise:

  1. The renderer runs Chromium with --allow-file-access-from-files, so the injected page gets an arbitrary local file read from a file:// origin.
  2. It also runs with --disable-web-security, which removes the same-origin policy, so that page can issue arbitrary cross-origin requests and read the responses.
  3. A second chromedriver listens on loopback as a more privileged user, with --allowed-origins='*' and --allowed-ips=127.0.0.1.

That last line is the one worth staring at. --allowed-ips=127.0.0.1 is a real control, correctly implemented, doing exactly what it says. And it is worth nothing here, because the attacker's JavaScript is already executing on 127.0.0.1. The allowlist is checking a property the attacker inherited for free.

File read alone was not enough; the flag path was randomised. The pivot to the privileged automation endpoint is what turned a read into a takeover. The IP check never stood a chance, because it was never guarding a boundary. It was guarding a location, and the attacker was handed that location by the architecture.

03Where this shows up for real

Once you have the shape, you see it everywhere. Four places it has cost real money:

Cloud instance metadata

The canonical case. 169.254.169.254 hands out credentials to anything that can reach it, on the theory that only the instance can. Then the instance runs an application with an SSRF bug, and "only the instance" starts including anyone on the internet who can make that application fetch a URL. IMDSv2 fixed this by requiring a token obtained via PUT with a hop limit, which is the right shape: prove you are the workload, do not merely originate from it.

CI runners

A build runner is a machine that executes untrusted code by design; that is its entire job. Anything it can reach without credentials is reachable by whoever opened the pull request. Internal package registries that trust the build network, deployment APIs bound to the runner subnet, Docker sockets mounted for "convenience": all of them are allowlisting a location the attacker was invited into.

Sidecars and localhost admin ports

In a Kubernetes pod, containers share a network namespace. A debug endpoint bound to 127.0.0.1 in one container is reachable from every other container in that pod. Spring Boot Actuator's /env and /heapdump are the usual casualties: not exposed to the cluster, perfectly exposed to the sidecar that got popped.

Headless browsers and renderers

Any service that renders attacker-controlled content is a foothold on its own host. PDF generators, screenshot services, link unfurlers, preview thumbnailers. If that renderer has network access, treat it as an unauthenticated user agent sitting inside your trust boundary, because it is one.

04How to actually fix it

The fix is always the same move: replace "where did this come from" with "what can you prove".

  • Authenticate the caller, not the interface. A loopback admin port still needs a credential. "Only local processes can reach it" is a statement about your network, not about your attacker.
  • Give renderers their own blast radius. No network egress, no loopback access to anything privileged, a dedicated unprivileged user, and a filesystem that contains nothing worth reading. Never --disable-web-security on a process that touches attacker input.
  • Make the trusted zone small enough to describe. If you cannot name every process that can reach a service, the allowlist protecting it is decorative.
  • Prefer proof of possession. Tokens, mTLS, signed requests, hop limits. All of them survive the attacker standing in the right place; an IP check does not.

Network position used to be a decent proxy for identity, back when a machine ran one thing and the perimeter meant something. It has been a bad proxy for a decade, and every container, sidecar and build runner you add makes it worse. The allowlist is not wrong. It is answering a question nobody is asking.
